# Git Workflow & Commit Standards (`AI_Job_Application_Agent`)

## 1. Commit Message Conventions
- **One-Line Concise Commits**: Always write short, single-line commit messages following Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`).
- **No Verbose Bodies**: Avoid long, multi-paragraph commit bodies unless explicitly requested by the user. Example:
  - ✅ `feat: add career preferences tab and vertical sidebar to profile editor`
  - ✅ `fix: handle missing career_preferences column gracefully in profile API`
  - ❌ `feat: add career preferences... \n\nThis commit updates profile-editor.tsx with 8 new tabs...`

## 2. Branching & Pull Request Workflow
- **Never Commit Directly to `main`**: All feature development and bug fixes must occur on `dev` or dedicated feature branches (`feat/*`, `fix/*`).
- **Pull Request Creation**: When changes on `dev` are ready for integration into `main`, create a Pull Request with `@coderabbitai review` in the PR body to trigger automated code review before merging.
- **CodeRabbit Review Triage**: You do **not** need to fix or address every comment generated by `@coderabbitai`. Triage comments into three categories:
  - **Must Fix (Critical/Bugs/Security)**: Always resolve actual logic errors, unhandled edge cases, null/undefined safety hazards, security vulnerabilities, or performance regressions.
  - **Evaluate & Apply (Improvements)**: Apply valuable suggestions (e.g., cleaner syntax, helpful error handling) if they align with the project's architecture and do not introduce scope creep.
  - **Ignore / Justify (False Positives/Nitpicks)**: Do not fix subjective style nitpicks, premature abstractions, or false positives (where the AI misunderstands framework behavior or business requirements). You can reply to CodeRabbit explaining why the code is intentional, use `@coderabbitai ignore`, or resolve the conversation without changes.
- **Atomic Checkpoints**: Commit changes in small, logical units (e.g., separate database schema migrations from UI refactors when feasible) so individual features can be cleanly reverted (`git revert <hash>`) if regressions occur.

## 3. Windows Environment Execution Invariance
- Due to Windows NUL device redirection restrictions inside the terminal sandbox (`Access is denied`), local read-only and non-remote-mutating `git` commands (`git add`, `git commit`) may be executed using `unsandboxed` action permissions when necessary.
- Remote-mutating operations (`git push`, `git fetch --prune`, `git pull --rebase`, etc.) must NOT be executed in unsandboxed mode by default. These commands require explicit user confirmation or should be provided to the user to run manually in PowerShell.

## 4. Security Rules — see `SECURITY.md`

Full rules live in `SECURITY.md` at the repo root; read it before touching auth, storage, database migrations, API routes, or any AI-calling code. The essentials, repeated here so they're never missed:

- Every new table gets RLS enabled in the *same* migration that creates it, using the `to authenticated` + `(select auth.uid())` policy pattern already used on `profiles`/`job_applications`/`resumes`.
- Never call `getPublicUrl()` on a private storage bucket — use `createSignedUrl()`, short expiry, generated per request.
- Any storage upload path must match the target bucket's RLS folder policy exactly (first path segment = the user's UUID).
- Never commit a real credential anywhere, including `.env.example` — placeholders only. If one is ever found committed, rotate it before doing anything else.
- Every API route calls `requireUser()` first; every mutation is scoped by `user.id` in the query itself; every update payload uses an explicit field allowlist, never a raw body spread.
- Never silently drop a field that failed to persist and still return 200.
- Resume/job text fed to an LLM is untrusted data — delimit it and instruct the model not to follow instructions found inside it.
- `SECURITY.md` currently lists several `[ACTIVE ISSUE]` items (see `AUDIT_AND_ROADMAP.md` for full detail) that must be fixed before Phase 2 work starts — check that file before assuming a rule below is already satisfied in the codebase.
